Ты подключаешься к разработке ТОЛК — SaaS-платформы для российских психологов
на Next.js + Supabase + YandexGPT, с AI-ассистентом (function calling, 18
инструментов) внутри продукта. Прод: https://tolk-three.vercel.app.
Репозиторий: https://github.com/Whisper-t3ch/tolk (ветка main).

## КРИТИЧНО ПРО ДЕНЬГИ — прочитай прежде чем что-либо тестировать

Есть два аккаунта Yandex Cloud:
- **Основной аккаунт** — только для реальной инфраструктуры беты (боевые
  ключи в Vercel Production: YANDEX_GPT_API_KEY, YANDEX_GPT_FOLDER_ID,
  YANDEX_SEARCH_API_KEY). НЕ ТРОГАТЬ трафиком тестов.
- **Тестовый аккаунт** — покрывается грантом, тратит грант, а не деньги
  пользователя. ИМЕННО СЮДА должны идти все тестовые вызовы.

Значит: **никогда не гоняй тестовые запросы через https://tolk-three.vercel.app
напрямую** (это Production = боевой ключ = основной аккаунт = реальные деньги).
Для тестирования используй одно из:
1. Preview-деплой Vercel (запушь в любую ветку, отличную от main — Vercel
   сам поднимает Preview URL, там подтянутся тестовые Preview/Development
   переменные окружения, НЕ боевые).
2. Локальный `npm run dev` с `.env.local`, где вписаны ТЕСТОВЫЕ значения
   YANDEX_GPT_API_KEY / YANDEX_GPT_FOLDER_ID (спроси у пользователя, если
   их нет под рукой — НЕ бери значения из Vercel Production).

Если сомневаешься, на каком ключе выполняется запрос — остановись и спроси
пользователя, не угадывай.

## Что уже сделано (не переизобретай)

- Агентский цикл с function calling, до 5 итераций, 18 инструментов
  (create_client, create_session, search_knowledge_base, send_session_invite
  и т.д.) — схема в `src/lib/agent/tools.ts`, выполнение в
  `src/lib/agent/executor.ts`, оркестрация в `src/app/api/assistant/route.ts`.
- ТРИ независимые попытки динамически/постоянно сузить список 18
  инструментов (topK, keyword routing, embedding retrieval) — ВСЕ
  провалились и были откачены. Постоянное удаление write-инструментов
  с UI-альтернативой — рассмотрено и отклонено (экономия токенов не
  оправдывает потерю UX). Эта ветка оптимизации закрыта, не предлагай её
  снова без явного запроса пользователя.
- Известный класс багов: YandexGPT Pro 5.1 нестабильно генерирует
  структурированные tool calls — иногда пишет псевдо-вызов текстом
  (перехватывается `pseudoToolCallParser.ts`), иногда заявляет о
  намерении не выполнив его ("сейчас проверю..."), иногда обещает
  результат действия текстом без вызова инструмента вообще (retry-
  эвристики в `route.ts`, ищи `looksLikeUnfulfilledIntent` и
  `looksLikeFakeWebSearchOffer`). Если увидишь новый вариант этого
  класса — расширяй существующую эвристику, не пиши новый параллельный
  механизм.
- Веб-поиск при пустой базе знаний — реализован как отдельный узкий
  путь (`/api/assistant/web-search`), НЕ 19-й инструмент в схеме.
  Yandex Search API ключ подтверждён рабочим.
- ОТКРЫТАЯ НАХОДКА (не решена): на тяжёлых клинических темах
  (диссоциативное расстройство идентичности, ПТСР от травмы) модель
  систематически отказывается вызывать search_knowledge_base — похоже
  на встроенный guardrail YandexGPT, не на случайную нестабильность.
  Requires дальнейшего исследования на других тяжёлых темах (суицид,
  самоповреждение, насилие) прежде чем делать выводы.

## Запись консультаций: переход с Jibri на браузерную запись (22.09)

### Принятые решения

Запись консультации переводится с серверного Jibri на **запись двух
аудиодорожек в браузере психолога**: его локальный микрофон и удалённая
дорожка клиента, полученная из WebRTC. На устройстве клиента не
запускается MediaRecorder, не используется IndexedDB под аудио и ничего
не выгружается — он участвует в обычном звонке и видит индикатор записи.
Фрагменты по 15-30 секунд выгружаются в объектное хранилище по мере
записи, после остановки браузер присылает manifest, backend проверяет
целостность и только потом отдаёт запись в GigaAM.

Решения пользователя, принятые явно (не переоткрывай без запроса):
- **Интеграция: lib-jitsi-meet со своим UI звонка.** Не iframe, не patch
  внутри сборки Jitsi.
- **ВМ ещё нет.** Инфраструктуры не существует, `NEXT_PUBLIC_JITSI_DOMAIN`
  не задан, реальные звонки сейчас протестировать негде.
- **Jibri заменяется полностью**, не остаётся как fallback.

### Блокер, из-за которого это решение и потребовалось

Jitsi сейчас встроен в `src/app/(app)/session/[id]/page.tsx` как обычный
`<iframe src={videoRoomUrl}>` на чужом домене, даже без External API.
Из-за same-origin policy родительская страница **не может** получить
MediaStream дорожек из этого iframe: `getOriginalStream()` существует
только внутри контекста Jitsi. Локальный микрофон психолога доступен и
так (свой `getUserMedia`), а вот голос клиента — нет. Поэтому браузерная
запись обеих сторон невозможна, пока звонок живёт в чужом iframe; отсюда
и переход на lib-jitsi-meet.

### Что уже написано и проверено

- `src/lib/recording/` — ядро записи, не зависящее от Jitsi (на вход
  принимает готовые MediaStream): `types.ts`, `mime.ts` (runtime-выбор
  формата), `checksum.ts`, `trackRecorder.ts` (одна дорожка, нарезка,
  сквозная нумерация, переподключение клиента), `sessionRecorder.ts`
  (две дорожки + manifest), `preflight.ts` (проверка устройства и
  вердикт о допуске к записываемой консультации).
- `outputs/tests/recording_browser_check.mjs` — прогон в реальном
  Chromium через Playwright на синтетических потоках. 29 проверок,
  все зелёные: обе дорожки пишутся, нумерация без дыр, фрагменты
  непустые, дорожки содержат разный звук, manifest сходится с фактом,
  расхождение длительностей 0-1 мс. Запуск: `node outputs/tests/recording_browser_check.mjs`.
- `outputs/backend/migration_036_browser_recording.sql` — схема:
  `session_recording_chunks` (реестр фрагментов), `session_transcript_segments`
  (реплики со спикерами и таймкодами), manifest и heartbeat на `sessions`,
  новые статусы `uploading`/`incomplete`, `source='jitsi_browser'`.
  Прогнана на настоящем PostgreSQL 16 поверх реконструированной схемы:
  12 проверок, включая идемпотентность, RLS, отбой дублей и каскады.
  ЕЩЁ НЕ ПРИМЕНЕНА к реальному Supabase-проекту.

Важные детали, чтобы не наступить повторно:
- Фрагмент **не является самостоятельным аудиофайлом**: в WebM/Opus
  заголовок контейнера попадает только во фрагмент с sequence=0.
  Сборка/remux дорожки обязательна перед ASR.
- `CREATE POLICY` не имеет формы `IF NOT EXISTS` — без `drop policy if
  exists` миграция падает на повторном прогоне. Проверено, в 036
  исправлено. В `migration_034` та же проблема осталась (не трогали).
- В контейнерах без аудиоустройств `getUserMedia` падает с NotFoundError
  при любых флагах Chromium (`--use-fake-device-for-media-capture` и
  `--use-file-for-fake-audio-capture` проверены, `enumerateDevices` пуст).
  Поэтому у `runPreflight` есть параметр `getMicrophoneStream` — он же
  убирает повторный запрос микрофона, когда звонок уже держит дорожку.

### Что осталось

- Буфер IndexedDB и загрузчик фрагментов (retry/resume, idempotency key).
- API: выдача pre-signed upload URL, приём подтверждений, manifest,
  heartbeat. Хранилище пока не выбрано окончательно — deploy-док
  предлагал Supabase Storage (bucket `recordings`), в репо Storage
  нигде ещё не используется.
- Замена iframe на lib-jitsi-meet со своим UI звонка.
- Backend: сборка дорожек (FFmpeg), VAD, вызов GigaAM по двум дорожкам,
  сведение сегментов по таймкодам. Текущий `src/lib/asr.ts` принимает
  ОДИН `audio_url` и возвращает плоский текст — контракт придётся менять.
- Удаление Jibri-пути: `/api/webhooks/recording` и раздел про Jibri в
  `outputs/backend/deploy_jitsi_gigaam.md`. Учти: `session_transcripts.raw_text`
  остаётся источником для SOAP/суммаризации/RAG — он собирается из
  сегментов как диалог, чтобы существующий пайплайн не пришлось трогать.

## Git-доступ этой cloud-сессии (важно для следующей сессии)

22.09 обнаружилась проблема, актуальная для ЛЮБОЙ облачной Claude-сессии
над этим репо, не только этой: исходящий git этой сессии идёт через
policy-proxy, который проверяет push (не только чтение) по отдельному
"authorized repository set", привязанному, похоже, к моменту СОЗДАНИЯ
сессии/задачи — а не к тому, что подключено потом. Проверено эмпирически:
ни личный GitHub PAT (чтение работало, push — нет), ни account-level
коннектор «GitHub Integration», добавленный постфактум через Connectors,
push не разблокировали — ошибка от прокси идентична во всех случаях:
`access denied by the git proxy: <repo> is not in this session's
authorized repository set`.

Если начинаешь новую сессию и тебе тоже нужен push: проверяй доступ сразу
(`git push --dry-run origin main` или любой безвредный push) и, если он
заблокирован той же ошибкой, не трать время на повторные попытки или
альтернативные токены — вместо этого ищи в интерфейсе Cowork/claude.ai
явный пункт выбора GitHub-репозитория ИМЕННО при создании задачи/сессии
(до первого сообщения), а не в общих настройках коннекторов постфактум.

## Протокол тестирования (соблюдай строго)

Пользователь установил жёсткое правило: если ХОТЯ БЫ ОДИН тест
показывает провал (нужный инструмент не сработал, модель не справилась) —
откатываем изменение ПОЛНОСТЬЮ, не патчим точечно. Это применялось трижды
подряд к попыткам сузить список инструментов. Уважай этот протокол для
любых экспериментов с оптимизацией стоимости/схемы.

## Стиль работы пользователя

- Просит SQL-проверки вместо предположений — "сначала проверить через SQL"
  повторяющийся паттерн.
- Требует точных логов (Vercel Logs, конкретный request_id) как
  доказательство, не довольствуется "похоже заработало".
- Явно против удаления функциональности "на всякий случай снизить число
  инструментов" без количественного обоснования.
- Ценит честные отчёты о найденных проблемах даже когда основная задача
  выполнена — не скрывай сопутствующие находки.
