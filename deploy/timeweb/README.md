# Приёмка серверов Таймвеб (2 ВМ: ASR и ядро)

Цель: за ~1 час и несколько десятков рублей (почасовая оплата) понять, какая линейка процессоров подходит. Тесты проводить ПОСЛЕ одобрения гранта (по условиям грант только для тех, кто ещё не был клиентом).

## Что сравниваем
Для ASR-сервера (8 vCPU / 16 ГБ): Premium 3,3 ГГц (разделяемые vCPU) против Dedicated CPU 3,3 ГГц и/или High CPU 5,5 ГГц (возможно, 4-6 vCPU). Ядро (4 vCPU / 8 ГБ) на Premium.

## Шаги на каждом сервере
1. Скопировать `hw_probe.sh` и запустить на простаивающем сервере: `./hw_probe.sh 5 <метка>` (метка: premium33, dedicated33, high55). Сохраняет `hw_<метка>.txt`.
2. ASR-сервер: развернуть `asr-service` как на Яндексе, затем `deploy/loadtest/asr_bench.sh baseline <10-минутный файл> 3` и `... burst <файл> 4 4` (параллельно 4 задачи). Для сравнения с Яндексом: RTF 0,064 (8 потоков).
3. Ядро: развернуть Supabase (`deploy/supabase/sb.sh`), сайт и Jitsi; `deploy/loadtest/run_load.sh <аудио> 20 12 1` (20 психологов, 12 минут), параллельно монитор `monitor_stack.sh`.
4. Jitsi: `deploy/loadtest/jitsi/jitsi_load.mjs` с отдельного генератора (не на этом сервере), P2P выкл., 5-7 комнат; смотреть CPU JVB и сеть.

## Критерии приёмки
| Проверка | Годно | Негодно |
|---|---|---|
| steal при нагрузке на все vCPU (hw_probe) | среднее < 3%, максимум < 10% | среднее > 5% |
| ASR RTF baseline (8 vCPU) | не хуже 0,08 | хуже 0,10 или большой разброс между прогонами |
| ASR при 4 параллельных задачах | очередь без ошибок, время растёт линейно | ошибки, таймауты |
| Ядро при 20 психологах (run_load) | CPU < 70%, ответы БД < 0,3 с | выше |
| Jitsi, 7 комнат без P2P | все вошли, CPU JVB < 30% одного ядра | отвалились участники |
| Запись на диск | > 200 МБ/с | < 100 МБ/с |

Решение: берём самую дешёвую линейку, где все строки «годно». Если Premium нестабилен по steal или RTF, пробуем Dedicated 3,3, затем High CPU с меньшим числом vCPU (4-6) и сравниваем цену за прогнанную нагрузку.

## Перед заказом спросить у Таймвеба
Открыт ли входящий UDP 10000 (Jitsi) и управляемый файрвол; гарантии CPU на каждой линейке; смена линейки без пересоздания; бэкапы и копия вне сервера; документы 152-ФЗ.

## После приёмки
Перенос данных (`deploy/supabase/migrate_from_cloud.sh`), смена DNS (только по команде владельца), бэкапы по расписанию, остановка ненужных ВМ (остановленные ВМ платят за диск и IP).
